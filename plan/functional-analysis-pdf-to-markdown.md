# Functional Analysis 두 교재의 Markdown·LaTeX 변환 계획

- 작성일: 2026-09-27
- 상태: 실행 전
- 입력: `Functional Analysis/source/Brezis.pdf`, `Functional Analysis/source/Conway.pdf`
- 출력 기준 위치: `Functional Analysis/md/`

## 1. 목표와 확정된 요구사항

두 교재를 원문에 충실한 장별 Markdown으로 변환한다. 일반 문장은 원래 언어·표현을 유지하고, 인라인 수식과 독립 수식은 LaTeX로 전사한다.

- Chapter, Section, Theorem, Lemma, Proposition, Corollary, Definition, Proof, Remark, Example, Exercises 등의 명칭·번호·순서·문구를 보존한다.
- 문장을 번역·요약하거나 증명을 보충하지 않는다. 원본 오탈자도 임의로 수정하지 않는다.
- 장별 파일과 책별 목차를 제공한다. 서문·원래 목차·참고문헌·색인 등 앞뒤 부속 내용도 포함한다.
- 반복 머리말·쪽번호는 독서용 본문에서 제외하되 페이지 메타데이터에 보존한다. 실제 각주는 본문에 연결한다.
- 전 페이지를 원본 이미지와 대조한다. 비용 절감을 이유로 표본 검수만으로 대체하지 않는다.
- 원본에서 판독할 수 없는 부분은 본문에 표시하고 원본 조각 이미지를 연결한다. 문맥상 추정 복원 후보는 별도 검수 기록에 제시한다.
- 모든 Python 라이브러리는 uv가 관리하는 가상환경 안에서 설치·실행한다.

## 2. 사전 조사 결과

| 대상 | 확인된 사실 | 처리 방향 |
|---|---|---|
| Brezis | 614쪽. PDF 목차 항목 97개. 텍스트 추출 시 485쪽에서 비정상 제어문자 검출. 표본에서 수학 기호·분수·첨자 구조의 추출 오류 확인 | 정상적인 본문 텍스트를 보존하고 수식·오류 구간을 이미지 기준으로 변환 |
| Conway | 416쪽 모두 이미지 포함. PDF 목차 항목 없음. 표본의 기존 OCR에서 수학 기호·단어 오류 확인 | 이미지에서 재인식하고 기존 OCR은 비교 자료로 사용 |
| 실행 환경 | Windows PowerShell, uv 0.11.33, NVIDIA GeForce RTX 3060 Laptop GPU, VRAM 6GB | 로컬 소형 OCR 모델을 우선 사용하고 실제 메모리 사용량 측정 |

표본 이미지는 Brezis PDF 21·308쪽과 Conway PDF 21·209쪽을 확인했으며 대체로 판독 가능했다. 텍스트 추출 오류와 원본 이미지 훼손을 구별해야 한다. 전체 페이지의 이미지 손상 여부는 아직 검수하지 않았다.

Brezis에서 텍스트가 추출되지 않은 PDF 페이지는 1, 3, 7, 11, 15, 45, 103, 195, 215, 277, 339, 363쪽이다. Conway에서는 1쪽이다. 이 목록은 빈 페이지 판정 결과가 아니며 이미지 확인이 필요하다.

조사는 uv 임시 환경의 PyMuPDF 1.28.2로 수행했다. OCR 모델의 정확도·속도·메모리 사용량은 아직 측정하지 않았다. 전체 분량은 1,030쪽이다.

## 3. 도구와 실행 환경

### 기본 구성

- `Functional Analysis/work/pdf-to-md/`에 Python 3.12 기반 uv 프로젝트를 구성한다.
- `pyproject.toml`과 `uv.lock`으로 검증된 의존성 버전을 고정하고 `uv run`으로 실행한다.
- PyMuPDF로 텍스트·좌표·폰트·목차를 추출하고 페이지·수식 영역을 렌더링한다.
- 기본 OCR은 MinerU의 로컬 `basic`·Torch 구성으로 한다. 조사 당시 공식 문서는 Windows/NVIDIA 4GB 이상 환경에 이 구성을 안내하며 수식·OCR·표 처리를 지원한다. 실제 6GB GPU에서의 호환성과 안정성은 표본으로 검증한다.
- Pix2Text는 수식과 텍스트가 섞인 영역의 재인식·비교용으로 사용한다. 의존성 충돌을 피하도록 별도 uv 환경에 설치한다.
- Windows용 CUDA PyTorch 설치와 `torch.cuda.is_available()` 확인을 실행 전 점검에 포함한다. nvidia-smi 성공만으로 Python GPU 실행 가능 여부를 판정하지 않는다.
- GPU 작업은 모델 하나, 페이지 한 장, 배치 크기 1부터 시작한다. 메모리 부족 시 모델을 순차 로드하고 영역별 처리로 전환한다. 계속 실패하면 해당 처리를 CPU로 수행하고 기록한다.
- 기본 실행은 로컬이며 문서를 외부 OCR 서비스나 별도 유료 API로 자동 전송하지 않는다. Codex에서 수행하는 이미지 검수는 Codex 모델 사용량을 소비하는 별도 단계다.
- 원본 파일 해시, 패키지·모델 버전, 모델 리비전, 설정, 실행 시간을 기록한다. 실행 시 공식 문서와 실제 설치 버전의 CLI·출력 형식을 확인한다.

## 4. 비용 관리와 subagent 운영

### 역할별 모델 배분

실제 구현·변환·검수 시 작업별 모델을 지정한 subagent를 사용한다. 단순한 계획 파일 저장에는 subagent를 실행하지 않는다.

| 작업 | 기본 선택 | 상향 조건 |
|---|---|---|
| PDF 추출, OCR, 페이지 목록, 링크·구문 검사 | 로컬 Python·GPU OCR | 모델 호출 없이 가능한 작업은 코드로 처리 |
| 파일 목록 정리, 명확한 형식 수정, 검수 기록 정리 | `gpt-6-luna`, low | 판단이 필요하거나 반복 오류가 나면 Sol로 이관 |
| 변환 코드 작성, 일반적인 문장·수식 대조, 구조 검수 | `gpt-6-sol`, medium | 복잡한 기호 구별이나 원본 해석이 해결되지 않으면 Astra로 이관 |
| 난해한 수식 판독, 원본 훼손의 추정 복원 후보 검토 | `gpt-6-astra`, medium부터 | 필요한 구간에서만 high로 상향 |

위 배분은 시작 설정이며, 표본 검수에서 품질을 충족하는 가장 가벼운 모델·추론 수준을 유지한다. 실행 시 해당 모델이나 이미지 입력 기능을 사용할 수 없으면 기능이 맞는 사용 가능한 모델로 조정하고 기록한다. 저비용 모델에 맡겼다는 이유만으로 검수 완료로 처리하지 않는다.

### 호출·컨텍스트 관리

- 주 에이전트는 단계 진행, 작업 분배, 결과 통합과 완료 조건을 관리한다. subagent에는 필요한 페이지 이미지·원문·해당 문서 규칙만 전달한다.
- 전체 대화나 책 전체를 모든 subagent에 반복 전달하지 않는다. 모델을 지정하는 subagent는 전체 대화 복제 대신 최소한의 독립 작업 지시를 사용한다.
- GPU OCR은 한 작업자로 순차 실행한다. subagent가 같은 GPU에 모델을 중복 로드하지 않도록 한다.
- 검수 작업은 책·페이지 범위별로 나누고 각 subagent가 별도 결과 파일에 기록한다. 최종 장별 MD의 통합은 한 작업자가 맡아 충돌을 방지한다.
- 완료된 페이지의 결과와 검수 이력을 저장한다. 원본·설정·모델·해당 출력이 바뀐 범위만 재처리한다.
- 이미지 판독에 충분한 해상도를 유지하되 불필요한 고해상도 전체 페이지 재전송을 피한다. 재검토는 관련 영역과 문맥을 전달한다.
- 동일 모델의 무변경 반복 호출을 피한다. 첫 검수에서 해결되지 않은 구간은 다른 인식 결과·원본 확대 등 새 근거를 추가하거나 상위 모델로 이관한다.
- 원본 훼손으로 정보가 없으면 반복 호출로 복구된 것처럼 만들지 않고 판독 불가와 복원 후보로 기록한다.

### 비용 기록과 통제

- 로컬 OCR 연산 자체에는 OpenAI API 토큰 요금이 발생하지 않지만, Codex의 지시·코드 작성·이미지 검수·subagent 사용은 모델 사용량을 소비한다.
- 우선 24쪽 표본의 모델별 호출 수, 제공되는 경우 입력·출력 토큰, 재검수 비율, 페이지당 시간을 기록한다. 관측 가능한 값으로 전체 예상 사용량을 산정하고 한계를 명시한다.
- 사용량 정보가 노출되지 않으면 정확한 토큰·금액을 추정한 것처럼 표시하지 않는다. Codex 구독 사용량과 별도 API 과금을 구별한다.
- 현재 합의된 금액·토큰 상한은 없다. 임의의 상한이나 유료 API 사용을 가정하지 않는다. 향후 사용자가 상한을 지정하면 배치 시작 전 잔여 예산을 확인하고, 상한 때문에 끝내지 못한 작업을 완료로 처리하지 않는다.
- 비용 때문에 전 페이지 검수를 생략하지 않는다. 절감은 로컬 처리, 적절한 모델, 최소 문맥, 중복 방지를 통해 수행한다.
- 주 대화 모델을 에이전트가 임의로 바꿀 수 있다고 가정하지 않는다. 역할별 모델 지정은 실제 제공되는 subagent 기능 범위 안에서 적용한다.

## 5. 실행 단계

### A. 전체 페이지 진단

1. 원본 PDF를 수정하지 않고 해시와 총 페이지 수를 기록한다.
2. PDF 페이지 번호와 책에 인쇄된 쪽번호를 구분한 1,030쪽 목록을 만든다. 로마 숫자, 무번호, 빈 페이지도 포함한다.
3. 렌더링 성공 여부, 텍스트·이미지 유무, 비정상 문자, 회전·잘림·번짐 의심 구간을 조사한다. 텍스트가 없다는 이유만으로 빈 페이지로 판단하지 않는다.
4. Brezis의 PDF 북마크와 두 책의 인쇄 목차를 대조해 장·절 경계를 정한다. 페이지 번호를 고정 오프셋만으로 추정하지 않는다.
5. 렌더링 실패 시 대체 PDF 렌더러로 재검사하고, 실패·손상 위치를 페이지 목록에 남긴다.

### B. 24쪽 표본 검증

각 책에서 12쪽을 선정한다. 목차, 장 시작, 정리·증명, 복잡한 인라인 수식, 다중 행 수식, 연습문제, 각주, 그림, 색인을 포함하고 손상 의심 페이지가 있으면 우선 포함한다. 선택한 페이지와 선택 이유를 기록한다.

- 기본 OCR과 원문 추출을 적용하고 원본 이미지와 자동 결과를 대조한다.
- 문장·수식 누락, 기호 오류, 읽기 순서, 번호 보존 여부를 기록한다.
- 수정 전후 결과, 페이지당 처리·검수 시간, 최대 VRAM과 관측 가능한 모델 사용량을 보존한다.
- 반복되는 수식 오류는 Pix2Text 재인식 대상으로 지정하고 해결되지 않은 영역은 직접 전사한다.
- 블록 누락·읽기 순서 오류를 해결하고 표본의 전사·렌더링 검수를 마친 뒤 전체 작업을 시작한다.
- 자동 처리와 이미지 대조 검수 시간을 구분해 전체 시간·비용을 추정한다.

### C. 책별 변환

#### Brezis

- 문단별 텍스트와 좌표를 추출한다.
- 이미지에서 인라인·독립 수식을 찾아 LaTeX로 변환한다.
- 일반 문장 중 정상 추출된 부분은 보존하며 수식 경계의 단어·공백과 비정상 문자 구간은 이미지와 대조한다.
- 전체 페이지 검수에서 검출기가 놓친 수학 표기도 확인한다.

#### Conway

- 기존 OCR을 정답으로 사용하지 않고 페이지 이미지에서 재인식한다.
- 원본 이미지 해상도를 확인하고 기본 300dpi로 렌더링한다. 작은 첨자는 영역을 확대해 재검사하되 확대를 정보 복구로 취급하지 않는다.
- 기울기·대비 보정은 파생 이미지에만 적용한다. 점·프라임·마이너스가 지워질 수 있으므로 원본과 보정본을 함께 확인한다.

#### 공통 구조 복원

- 원래 표제·번호·순서·문구와 수학적으로 의미 있는 글꼴 구별을 보존한다.
- 지면에 따른 줄바꿈·단어 분할만 연결한다. 실제 하이픈·구두점·강조를 유지한다.
- 페이지를 넘어가는 문단·증명·수식을 연결하고 각주·그림 설명·참고문헌·색인의 귀속을 확인한다.
- 그림이 PDF 벡터 객체로 되어 있으면 이미지 객체 추출만으로 누락되지 않도록 해당 영역을 렌더링한다.
- 자동 인식 결과, 검수 수정, 최종 문서를 분리한다. 검수 수정은 별도 패치·이력으로 관리해 재실행이 덮어쓰지 않게 한다.

### D. 전 페이지 검수와 통합

- 페이지별로 본문·인라인 수식·독립 수식·그림·표·각주를 원본 이미지와 대조한다.
- 읽을 수 있는 원본을 OCR이 잘못 인식한 경우 직접 전사해 해결한다.
- 판독 불가 구간은 표시·이미지·별도 복원 후보를 기록한다.
- 검수된 페이지들을 장별로 통합하고 장 경계·페이지 경계의 연결을 재검사한다.

| `review/` | 페이지 대응표, 검수 이력, 판독 불가 목록, 추정 복원 후보 |

중간 결과는 `Functional Analysis/work/pdf-to-md/` 아래에서 책별로 분리한다. 원본 추출, OCR 출력, 렌더 이미지, 교정 이력과 최종 MD를 구별한다.

페이지·블록 대응 정보에는 최소한 책 식별자, PDF 페이지, 인쇄 쪽번호, 원본 영역 좌표, 블록 종류, 읽기 순서, 추출 방식, 최종 MD 위치, 검수 상태를 포함한다. 인쇄 쪽번호를 알 수 없으면 미상으로 둔다.

검수 상태는 미처리, 자동 추출 완료, 대조 필요, 검수 완료, 원본 판독 불가를 구별한다. 원본 판독 불가는 이미지 대조를 마친 뒤 부여하며 전체 페이지의 검수 여부와 별도로 추적한다.

## 7. Markdown·LaTeX 표기 규칙

- 인라인 수식은 `$...$`, 독립 수식은 `$$...$$`를 사용한다.
- MathJax 호환 LaTeX로 분수·첨자·행렬·경우 구분·다중 행 수식을 표현한다.
- 수식 번호는 원래 번호를 명시하며 자동 재번호화하지 않는다. 렌더러에서 번호를 보존하는 방식을 표본 단계에서 검증한다.
- 굵은 글자·캘리그래픽·블랙보드 볼드·별표·켤레·프라임 등 의미 있는 기호 차이를 보존한다.
- 장·절은 Markdown 제목으로, 정리·증명 등의 표제는 원문 표기를 유지한 강조 문구로 표현한다.
- 반복 머리말·쪽번호는 페이지 메타데이터로 보존하고 페이지 경계는 HTML 주석으로 표시한다. 수식·단어 한가운데 주석을 삽입하지 않는다.
- 각주는 고유한 Markdown 각주 ID로 연결하되 원본 각주 번호를 대응 정보에 보존한다.
- 그림은 상대 경로 이미지로 연결하고 설명 문구는 전사한다. 표는 Markdown 표를 기본으로 하며 병합 셀이 필요하면 HTML 표로 표현한다.
- 원본 색인의 인쇄 쪽번호를 임의로 바꾸지 않는다.
- 본문이 판독 불가이면 `[판독 불가: 식별자]`와 원본 이미지 링크를 남긴다. 추정 복원 후보·근거·불확실성은 별도 검수 기록에만 적는다.

## 8. 검증 시나리오와 완료 조건

### 자동 검사

- 모든 PDF 페이지가 목록에 있으며 누락·중복이 없는지 검사한다.
- 파일·이미지·목차·각주 링크, 비정상 제어문자, 수식 구분자·괄호 닫힘과 Markdown 구조를 검사한다.
- Markdown을 MathJax로 렌더링해 모든 수식의 구문 오류와 표시 문제를 검사한다. 렌더링 성공을 원문 일치의 증거로 대체하지 않는다.
- 구조·번호 검사에서는 장·절마다 번호가 다시 시작되는 원본 관례를 고려한다.
- 중단 후 재개와 특정 페이지 재처리에서 출력 순서·완료 상태·교정 이력이 유지되는지 검증한다.

### 이미지 대조

- 총 1,030쪽 모두에 대해 문장·수식·표·그림 설명의 포함 여부와 읽기 순서를 확인한다.
- 정리·연습문제·수식 번호, 가정과 결론, 부정 기호, 부등호, 첨자, 적분 범위, 프라임을 대조한다.
- 페이지를 넘는 문장·증명·수식 연결, 각주 귀속과 장 경계를 확인한다.
- OCR 신뢰도나 두 엔진의 결과 일치만으로 검수 완료를 판정하지 않는다.

### 완료 판정

모든 페이지에 이미지 대조 기록이 있고, 발견된 전사·구조·렌더링 오류가 해결되며, 원본에서 복구할 수 없는 훼손이 모두 표시된 상태를 완료로 한다. 미검수 페이지나 알려진 미해결 전사 오류가 있으면 초안 또는 진행 중으로 보고한다.

최종 보고서는 처리·검수 페이지 수, 모델·도구 버전, 관측 가능한 사용량, 판독 불가 구간, 별도 추정 복원 후보와 제한 사항을 포함한다. 오류율 0%를 근거 없이 보장하지 않는다.
